MediaCMS / WAIC 素材平台框架设计评审

审查日期：2026-05-29
审查方式：基于仓库结构、核心配置、路由、前端构建配置与页面映射文档抽样分析
目标：总结当前代码框架设计中的主要问题，便于团队内部同步、转发和讨论

一、结论摘要

当前仓库整体上属于 Django 单体应用 + 多套前端形态并存 的演进型架构。

它的主要问题不是“某一层完全不可用”，而是：

后端路由、模板层、主前端、独立前端工具、静态构建产物之间边界不够清晰，系统已进入多代架构叠加状态，但尚未完成边界重整。

短期看，这种结构仍然支持功能迭代；但中长期会持续抬高以下成本：

  • 新功能接入成本
  • 新成员理解成本
  • 页面问题排查成本
  • 前端升级成本
  • 模块拆分与复用成本
  • 测试与配置治理成本

二、当前架构概览

1. 后端

后端以 Django 为核心，承担：

  • URL 路由聚合
  • 页面模板渲染
  • REST API
  • 用户认证与权限
  • 后台管理
  • 媒体处理相关业务

关键入口：

  • cms/urls.py
  • files/urls.py
  • users/urls.py
  • cms/settings.py

2. 主前端

主前端位于 frontend/，采用：

  • React 17
  • 自定义 mediacms-scripts
  • Webpack 风格构建链
  • 页面多入口方式

关键文件：

  • frontend/package.json
  • frontend/config/mediacms.config.js
  • frontend/config/mediacms.config.pages.js
  • frontend/src/static/js/utils/renderer.js

3. 独立前端工具

仓库内还存在多个独立前端子应用：

  • frontend-tools/video-editor/：React 18 + Vite
  • frontend-tools/chapters-editor/：React 18 + Vite
  • frontend-tools/video-js/：React 19 + Vite

这些工具不是主前端内部模块，而是各自独立构建后再集成到 Django 页面。

4. 页面组织方式

页面渲染链路通常为：

  1. Django URL
  2. Django View
  3. Django Template
  4. React 页面组件
  5. 页面构建配置
  6. 通用 Renderer 与 Layout 注入

仓库中已经存在一份人工维护的页面索引文档：FRONTEND_PAGES.md。

三、主要框架设计问题

问题 1：路由与页面入口过于集中，已经出现“总线文件膨胀”

现象

cms/urls.py 负责聚合多个一级入口，并且文件内已直接出现注释：

# refactor seriously

与此同时，files/urls.py 不仅负责媒体相关页面，还混合承载了：

  • 普通页面路由
  • API 路由
  • 管理端路由
  • 审批相关 API
  • 通知相关 API
  • 权限相关 API
  • 分享相关 API
  • 字幕上传与编辑
  • 文件下载与媒体 range 服务
  • 通用 slug 兜底页

尤其值得注意的是最后的 slug 兜底路由：

re_path(r"^(?P<slug>[\w.-]*)$", views.get_page, name="get_page")

为什么这是设计问题

这说明 files 模块已经不再只是“媒体域模块”，而逐渐承担了“站点业务主入口”的职责。

结果是：

  • 路由组织依赖人工记忆
  • 顺序敏感，容易被兜底路由影响
  • 页面、接口、管理端混在一起
  • 后续拆分难度越来越高

影响

  • 新功能不知道该放在哪个模块
  • 新页面新增时容易与现有兜底规则冲突
  • 测试边界模糊
  • files app 持续膨胀，成为“超级模块”

判断

这是当前最重要的结构问题之一，优先级 高。

问题 2：页面渲染链路过长，Source of Truth 不单一

现象

一个前端页面的完整入口往往需要同时跨越以下位置：

  • Django URL
  • Django View
  • Django Template
  • React 页面组件
  • 前端页面构建配置
  • 通用 renderer

FRONTEND_PAGES.md 中需要专门维护 URL、view、template、React page 的映射关系，说明页面结构本身并不够自解释。

为什么这是设计问题

多层结构本身不是问题，问题在于：

页面入口定义被分散在多个层级中，没有单一、稳定、显式的页面事实来源。

这样会导致页面的生命周期被多处共同拼装，而不是一个地方定义、其他地方消费。

影响

  • 页面定位路径长
  • 改一个页面经常要跨 3~5 个位置
  • 模板、构建配置、React 组件之间容易出现不同步
  • 页面问题排查成本高

判断

这是影响开发效率和可维护性的核心问题，优先级 高。

问题 3：cms/settings.py 承担了过多产品逻辑，配置中心过载

现象

cms/settings.py 不仅包含常规 Django 配置，还混入大量产品与展示层开关，例如：

  • 是否允许登录、注册、上传、点赞、举报、分享
  • 默认主题、Logo、额外 CSS
  • 页面可见性控制
  • 前端交互行为开关
  • 视频转写与处理策略
  • SAML / RBAC / LTI 等能力开关
  • UI 文案和展示相关配置

随后，这些配置又被 files/context_processors.py 批量注入到前端运行时上下文。

为什么这是设计问题

settings.py 适合承载：

  • 环境配置
  • 部署配置
  • 框架配置

但当前它还承担了大量：

  • 产品规则
  • 前端功能开关
  • 展示策略
  • UI 配置

这意味着：

后端配置文件已经成为整站产品行为的事实中心。

影响

  • 环境配置与业务策略耦合
  • 前端行为依赖后端隐式注入
  • 配置项数量持续增长，难以审计与测试
  • 修改一个前端行为，经常要同时理解 settings、template、context processor、React 页面

判断

这是典型的“早期方便、后期变重”的设计，优先级 高。

问题 4：前端体系分裂，已经形成多代技术栈并存

现象

当前仓库中至少并存三套前端体系：

子系统 技术栈 备注
主前端 React 17 + 自定义 Webpack 构建 核心主站
视频/章节编辑器 React 18 + Vite 独立工具页
Video.js 工具 React 19 + Vite 又一套前端版本

为什么这是设计问题

这不是单纯的“版本不同”，而是说明前端的演进路径已经分叉：

  • 主站仍停留在旧构建体系
  • 新工具页采用新一代构建方式
  • React 主版本不统一
  • 样式、工程规范、升级路径可能逐渐失去一致性

影响

  • 依赖升级复杂
  • 公共组件难复用
  • 前端工程治理难统一
  • 新成员需要理解多套构建方式
  • 后续如果要统一设计系统、埋点、监控、测试，会遇到额外阻力

判断

这是中长期影响最大的技术演进问题之一，优先级 高。

问题 5：源码与静态构建产物边界不清晰

现象

多个前端工具直接构建到仓库 static/ 目录，例如：

  • static/video_editor/
  • static/chapters_editor/
  • static/video_js/

主前端也依赖 static/ 下的资源。

为什么这是设计问题

当构建产物直接与仓库静态资源混在一起时，经常出现以下问题：

  • 很难一眼判断哪些文件是源码、哪些是产物
  • 容易有人直接修改产物文件救火
  • 重新构建后，人工修改可能被覆盖
  • diff 中可能混入大量构建噪音
  • 部署流程可能依赖“仓库里已有 build 结果”

影响

  • 回滚困难
  • 代码评审噪音大
  • 构建与发布边界模糊
  • 新成员容易误改静态产物

判断

这是典型的维护性问题，优先级 中高。

问题 6：files app 职责范围过宽，领域边界失真

现象

从命名上看，files 应当主要承载媒体/文件域逻辑；但从实际结构看，它已经覆盖：

  • 媒体页面
  • 媒体 API
  • 管理页
  • 审批流
  • 通知
  • 权限申请
  • 分享
  • 字幕
  • 转写
  • 水印下载
  • 媒体 range 传输
  • 通用 CMS 页面兜底

为什么这是设计问题

当一个模块名与实际职责范围明显不一致时，往往意味着：

  • 模块边界已经失效
  • 新功能会继续倾向于“先塞进去再说”
  • 后续拆分成本会越来越高

影响

  • 业务归属模糊
  • 代码审查难以按领域分工
  • 小改动可能影响多个无关能力
  • 很难形成清晰的模块 owner 机制

判断

这是架构命名与职责偏离的典型问题，优先级 高。

问题 7：Context Processor 承担了大量前端运行时配置，隐式依赖过重

现象

files/context_processors.py 会向前端注入大量运行时变量，包括：

  • 站点信息
  • 用户状态
  • 功能开关
  • 权限状态
  • 上传限制
  • 主题与 Logo
  • 翻译文本
  • 版本信息
  • LTI 会话信息

为什么这是设计问题

少量全局模板变量是合理的，但当大量页面行为依赖 context processor 时，就会使前端变成：

  • 一部分由 React 驱动
  • 一部分由 Django 模板注入驱动
  • 一部分由 settings 开关驱动

也就是说，前端运行条件不够显式，属于隐式依赖过多。

影响

  • 前端独立测试难度增加
  • 组件复用能力下降
  • 页面行为对服务端上下文过于敏感
  • 本地 mock 与调试复杂

判断

这属于结构可解释性不足的问题，优先级 中高。

问题 8：主前端 renderer 入口逻辑承担了过多兼容职责

现象

frontend/src/static/js/utils/renderer.js 需要兼容：

  • embedded app
  • 普通页面
  • 仅内容区
  • 仅 header / sidebar 的不同挂载情况

这说明页面外壳结构并不完全统一，renderer 正在承担历史兼容层的角色。

为什么这是设计问题

前端入口层本应尽量简单稳定：

  • 找到挂载点
  • 挂载页面
  • 注入必要 provider

如果入口层需要处理大量“页面结构分支”，往往说明模板契约不够稳定，或者旧页面与新页面没有收敛到统一页面壳模型。

影响

  • 入口层变脆
  • 布局问题排查成本高
  • 后续统一页面结构更难推进

判断

属于中优先级结构问题。

问题 9：系统理解高度依赖人工索引文档，代码结构自解释能力偏弱

现象

仓库内已存在较详细的 FRONTEND_PAGES.md，用于解释页面 URL、模板、React 页面、配置入口之间的对应关系。

为什么这是设计问题

文档本身是好事，但如果系统必须依赖额外人工索引文档，才能快速理解页面结构，通常说明：

  • 页面定义分散
  • 约定不够统一
  • 命名与职责边界不够自然
  • 代码结构缺少直接表达力

影响

  • 文档一旦滞后就会误导
  • 理解系统需要同时依赖代码和手工地图
  • 新成员 onboarding 时间变长

判断

这是可维护性问题，优先级 中。

四、次一级问题

除上述核心问题外，还存在一些次一级但值得关注的信号：

1. 环境配置、部署细节、默认值、业务开关混杂

cms/settings.py 中同时出现：

  • ALLOWED_HOSTS = ["*", ...]
  • 数据库默认连接信息
  • Redis 默认地址
  • 邮件默认配置
  • 媒体处理命令路径
  • UI 及产品行为开关

这进一步说明配置职责没有被很好分层。

2. Python 工程治理信息偏弱

pyproject.toml 当前几乎只包含 Black 配置，看不到更完整的项目工程治理中心信息。

3. 前端风格处于跨代混合状态

从页面结构可见：

  • .js 与 .tsx 混用
  • class 组件思路与函数组件思路可能并存
  • 页面基类 _Page.js、_MediaPage.js、_VideoMediaPage.js 等历史抽象仍在发挥作用

这不是立刻致命的问题，但说明主前端尚未完成统一风格收敛。

五、按严重性排序

高优先级

  1. 路由与页面入口过于分散，files app 逐渐成为超级模块
  2. 页面渲染链路过长，Source of Truth 不单一
  3. cms/settings.py 过载，环境配置与产品逻辑强耦合
  4. 前端体系分裂，React / 构建工具多代并存
  5. files 模块职责范围失真，领域边界不清

中优先级

  1. 静态构建产物与源码边界模糊
  2. context processor 向前端注入过多运行时配置
  3. renderer 入口承担过多历史兼容逻辑
  4. 系统理解依赖人工索引文档

中低优先级

  1. Python 工程治理中心较弱
  2. 前端风格与抽象跨代混用

六、适用阶段判断

当前架构适合

  • 小团队持续维护
  • 需求变化快、优先交付
  • 历史系统逐步扩展
  • 功能多于治理的阶段

当前架构不适合

  • 多团队并行长期演进
  • 想统一前端工程体系
  • 想建立清晰的模块 ownership
  • 想显著降低新人接手成本
  • 想逐步走向更稳定的测试与发布治理

七、总评

一句话总结：

这个项目当前最大的框架设计问题，不是单个模块写得差，而是系统已经形成“多代架构叠加”的状态，但模块边界、页面边界、配置边界、前端边界还没有同步重整。

因此，当前最典型的架构症状是：

  • Django 既像后端，又像页面编排器，又像前端配置中心
  • 主前端与多个工具前端各自演进
  • files app 被不断扩展为业务主入口
  • 页面渲染链路跨越多个层级
  • 文档正在替架构本身承担解释成本

如果继续按当前结构堆叠功能，系统短期仍可工作，但中长期维护成本会持续上升。

八、建议的后续讨论方向

本评审文档聚焦“问题识别”，不展开详细改造方案。

如果后续需要继续推进，可进一步输出以下文档之一：

  1. 架构问题清单 + 优先级 + 分阶段重构路线图
  2. 按目录逐项点评（cms / files / frontend / frontend-tools）
  3. 页面架构重整建议（路由、模板、React 页面入口统一）
  4. 前端工程统一建议（React 版本、构建链、静态产物策略）

  • users/urls.py
  • files/context_processors.py
  • frontend/package.json

  • frontend/src/static/js/utils/renderer.js

  • Celery 任务与媒体处理职责边界
